# 测试开发与质量工程转型计划

## 一、转型目标

从以执行功能测试为主，逐步转向能够建设自动化、测试平台、质量流程和线上保障能力的 **测试开发工程师（SDET）/ 质量工程师（QE）**。

核心定位：

> 从“执行测试的人”，成长为“搭建质量保障能力的人”。

当前正在开发的测试工具是转型的核心作品，应持续把它建设成可演示、可部署、可复用的工程项目。

## 二、职业方向选择

| 方向 | 主要工作内容 | 与当前工作的关联 |
| --- | --- | --- |
| 测试开发 / SDET（优先） | 自动化测试、测试平台、接口与性能测试、持续集成 | 直接延续测试工具开发 |
| 质量工程 / QE | 测试左移、质量度量、发布准入、线上质量治理 | 利用已有业务与测试经验 |
| 工程效能 / DevOps（质量方向） | CI/CD、环境管理、自动化发布、可观测性 | 可在测试开发基础上延伸 |

建议主线：**测试开发 / SDET → 质量工程 / 工程效能能力扩展**。

## 三、6 个月行动路线

```text
测试工具
  → 接口自动化平台
  → 定时回归 + 测试报告 + 消息通知
  → CI/CD 发布准入
  → 质量数据看板
  → 线上巡检与异常告警
```

### 阶段 1：把测试工具做成可展示的作品（第 1～2 个月）

目标：完成一个能够解决真实测试效率问题、可独立部署和演示的最小闭环。

#### 功能优先级

1. 接口测试
   - 配置 HTTP 请求、Header、参数和请求体。
   - 支持环境切换与变量引用。
   - 支持状态码、字段值、响应时间等断言。
   - 支持测试用例集合、批量执行和结果汇总。

2. 自动化执行
   - 支持定时任务。
   - 支持失败重试。
   - 支持企业微信、钉钉或邮件通知。

3. 数据与追溯
   - 保存每次执行记录、失败日志和耗时。
   - 展示接口或模块的历史通过率和失败趋势。
   - 支持用例导入、导出或模板复用。

4. 工程化交付
   - 用 Git 管理代码和版本。
   - 用 Docker 完成一键部署。
   - 编写 README、架构图、部署说明和使用示例。
   - 预留 CI/CD 调用入口。

#### 阶段产出

- 一个可运行的测试工具版本。
- 一段 5～10 分钟的演示流程：创建用例 → 执行 → 查看报告 → 接收通知。
- 一份项目说明：解决的问题、技术方案、使用方式和后续规划。

### 阶段 2：补齐测试开发核心能力（第 2～4 个月）

目标：能够独立开发测试服务，并将测试接入研发交付流程。

| 能力 | 学习与实践重点 |
| --- | --- |
| 编程语言 | Python 或 Java 选择一门作为主语言；优先深挖当前工具使用的语言。若团队研发以 Java 为主，逐步补 Java。 |
| 接口自动化 | Python：`pytest + requests`；Java：`JUnit + RestAssured`。把框架用于真实接口回归。 |
| UI 自动化 | 优先学习 Playwright，掌握页面对象模型、等待机制、稳定性处理和报告。 |
| 数据库 | MySQL 查询、索引、事务、测试数据准备与校验。 |
| 中间件 | Redis 基础；了解 Kafka 或 RabbitMQ 的消息验证方法。 |
| Linux | 日志排查、Shell 基础、进程、端口和网络排障。 |
| 工程化 | Git 分支协作、Docker、Jenkins 或 GitLab CI。 |
| 性能测试 | JMeter 或 k6，能完成压测设计、执行和结果分析。 |
| AI 辅助 | 用 AI 生成用例骨架、分析日志、补全断言；关键判断、代码审查和结果验证自己负责。 |

执行原则：**每学习一项能力，都要在测试工具或实际项目中落地一次。**

### 阶段 3：升级为质量体系能力（第 4～6 个月）

目标：不止会写自动化脚本，还能推动团队质量流程和质量数据建设。

- 建立核心业务链路的接口自动化回归。
- 将自动化测试接入提测、代码合并或上线前流水线。
- 建立发布准入规则：核心用例未通过时阻断或预警发布。
- 建设质量看板：回归通过率、缺陷趋势、线上问题、接口稳定性。
- 建设线上巡检：定时探测核心接口，异常时自动告警。
- 在需求评审阶段补充边界条件、异常流程和可测性要求，推动测试左移。
- 沉淀公共能力：测试数据构造、Mock、环境管理、日志检索。

#### 阶段产出

- 一套自动化回归流程。
- 一个可查看的质量看板或测试报告中心。
- 一份发布准入规则与线上巡检方案。
- 至少 1 个可量化的改进案例，例如：回归时间缩短、核心接口覆盖率提升、线上问题提前发现。

## 四、每周执行节奏

| 时间投入 | 建议事项 |
| --- | --- |
| 每周 2～3 小时 | 学习一个与当前迭代直接相关的技术点。 |
| 每周 4～6 小时 | 为测试工具完成一个可演示的小功能或工程化改进。 |
| 每周 1 小时 | 记录问题、方案、结果和技术笔记。 |
| 每月半天 | 复盘项目进度，更新作品说明、截图和成果数据。 |

## 五、成果量化与简历沉淀

每项工作都尽量记录“改进前 / 做了什么 / 改进后”的数据。

可记录指标：

- 自动化覆盖的接口、场景或核心链路数量。
- 回归执行耗时和人工投入变化。
- 自动化执行通过率、失败率和稳定性。
- 发现的缺陷数、提前发现的线上风险数。
- 已接入的项目、环境或流水线数量。
- 团队实际使用人数与使用频率。

简历表达示例：

> 独立设计并开发接口自动化测试平台，支持环境变量、断言、批量执行、定时回归、测试报告和失败告警；接入 CI/CD 流水线，实现核心接口上线前自动校验，降低人工回归成本并提升发布质量可控性。

## 六、近期优先事项

1. 明确当前测试工具的首个用户和最核心场景。
2. 先完成“接口用例 → 执行 → 报告 → 通知”的最小闭环。
3. 为项目补齐 README、部署方式和演示材料。
4. 选择 Python 或 Java 作为主攻语言，并围绕工具持续实践。
5. 在 2 个月内做出可演示版本，在 6 个月内形成自动化、流水线和质量度量闭环。

## 七、判断转型是否成功

当你能够清楚回答以下问题时，说明已经具备测试开发 / 质量工程岗位的核心竞争力：

- 如何设计一套可维护的自动化测试方案？
- 如何让测试在 CI/CD 中自动运行并影响发布决策？
- 如何定位自动化失败、接口异常或线上问题？
- 如何用质量数据说明风险和改进价值？
- 如何把重复测试工作沉淀为团队可复用的平台能力？
